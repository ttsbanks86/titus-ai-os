## Disclaimer

This document describes a proposed future project. It is not under active development. All scenarios, assignments, and stakeholders referenced are fictional and created for BA portfolio development purposes. No real company data, client information, or business outcomes are claimed.

---

## 1. Training Objectives

The BA Compass Work Simulation Lab exists to let aspiring and junior Business Analysts practice core BA skills in a safe, repeatable environment. Unlike real projects, there are no career consequences for mistakes, no budget overruns, and no reputational risk. The lab targets these objectives:

- Practice stakeholder elicitation without real interpersonal pressure
- Write requirements documents and user stories with immediate feedback
- Learn to handle scope changes, conflicting priorities, and unclear requests
- Build a portfolio of practice deliverables that demonstrate BA competency
- Develop pattern recognition for common BA scenarios and anti-patterns
- Accelerate the transition from theoretical BA knowledge to practical application

---

## 2. Simulation Structure

Each simulation follows a consistent lifecycle:

**Phase 1: Briefing** (5-10% of time)
- Receive an email or message from a manager or stakeholder
- Read background context documents
- Review simulation rules and success criteria

**Phase 2: Discovery** (20-25% of time)
- Ask clarifying questions (to the AI-simulated stakeholder)
- Research existing documentation
- Identify missing information and assumptions

**Phase 3: Analysis** (30-40% of time)
- Map processes, analyze gaps, or model requirements
- Apply BA techniques (process mapping, MoSCoW, gap analysis, etc.)
- Document findings in structured formats

**Phase 4: Delivery** (20-25% of time)
- Produce the required deliverables
- Review against quality criteria
- Submit for feedback

**Phase 5: Reflection** (10% of time)
- Self-review against scoring rubric
- Compare to model answer
- Identify skill gaps for future simulations

All simulations are time-boxed. Each phase has a suggested time allocation to build real-world discipline.

## 3. Difficulty Levels

### Beginner
- Single stakeholder, clear domain, well-defined problem
- Templates provided for all deliverables
- No ambiguity in the request
- 30-45 minute time limit
- Example: Document a simple process flow

### Intermediate
- Multiple stakeholders with aligned interests
- Some ambiguity in requirements
- Must choose between BA techniques
- 45-75 minute time limit
- Example: Elicit requirements from two stakeholders, produce a BRD section

### Advanced
- Stakeholders with conflicting priorities
- Deliberately vague or misleading initial request
- Must manage a scope change or escalation event mid-simulation
- 75-120 minute time limit
- Example: Full requirements gathering with conflicting stakeholder priorities and a mid-session regulation change

## 4. AI Roles

In the future implementation, the AI would simulate these roles:

| Role | Behavior | Communication Style |
|------|----------|-------------------|
| **Manager** | Gives vague requests, expects progress updates, changes mind | Email, short messages |
| **Operations Lead** | Wants speed above all, impatient with process | Direct, blunt, interrupts |
| **Compliance Officer** | Cites regulations, demands documentation | Formal, references policies |
| **Scheduling Coordinator** | Knows the real process, feels unheard | Informal, detailed, slightly frustrated |
| **IT Admin** | Technical constraints, cares about integration | Precise, jargon-heavy |
| **Client Representative** | Non-technical, describes wants not needs | Lay language, emotional |
| **Agency Owner** | Strategic view, ROI-focused, asks hard questions | Executive tone, concise |
| **Caregiver** | Frontline perspective, practical concerns | Casual, experience-driven |

Each role has a personality profile, known concerns, and a hidden agenda that affects how they answer questions. The user must navigate these dynamics to extract accurate requirements.

## 5. User Role

The user always acts as a **Business Analyst** contracted or employed by BrightCare Home Services (or another fictional company depending on the scenario). They are expected to:

- Behave professionally and proactively
- Ask clarifying questions rather than assume
- Document requirements in standard BA formats
- Manage stakeholder relationships
- Adapt to changing circumstances
- Deliver clear, actionable outputs

The user is never given complete information upfront. They must discover it through elicitation.

## 6. Example Assignments by Level

### Beginner Assignments

1. **Document the Current Process** — A scheduling coordinator describes how shifts are assigned. Create a process map.
2. **Write a Project Charter** — Given a one-paragraph problem statement, produce a full project charter.
3. **Create a Stakeholder List** — From a case description, identify all stakeholders and classify them on a power/interest grid.

### Intermediate Assignments

1. **Requirements Elicitation** — Interview two stakeholders with different needs. Produce a prioritized requirements list with MoSCoW classification.
2. **Gap Analysis** — Given current and desired state descriptions, produce a gap analysis with recommendations.
3. **User Story Workshop** — Facilitate (via AI) a user story writing session. Output a backlog with acceptance criteria.

### Advanced Assignments

1. **Full BRD with Conflicting Stakeholders** — Operations wants speed, Compliance wants documentation. Produce a BRD that satisfies both.
2. **Scope Change Management** — Requirements are 80% drafted when a regulatory change forces new data collection. Assess impact, update documents, communicate.
3. **UAT Management** — A system is delivered. Design test scenarios, execute them against provided data, find defects, write bug reports, and recommend go/no-go.

## 8. Scoring Rubric

Each deliverable is scored on a 1-5 scale across these dimensions:

| Dimension | 1 (Needs Work) | 3 (Meets Expectations) | 5 (Exemplary) |
|-----------|----------------|------------------------|----------------|
| **Completeness** | Major sections missing or empty | All required sections present with content | Thorough coverage of all sections with proactive extras |
| **Clarity** | Confusing or contradictory content | Clear language, logical flow, easy to follow | Professional quality, could be used as a real-world example |
| **Traceability** | No links between elements | Requirements can be traced to sources | Full traceability with rationale preserved |
| **Stakeholder Consideration** | Only one perspective reflected | Multiple stakeholder needs addressed | Conflicts identified and resolved, rationale documented |
| **BA Technique Application** | Wrong technique or incorrect application | Appropriate technique applied correctly | Technique adapted creatively to the scenario |
| **Professional Presentation** | Formatting errors, typos, inconsistent | Clean formatting, professional tone | Publication-ready, consistent style throughout |

Each simulation has a weighted score. The overall rubric weights vary by assignment (e.g., a process mapping exercise weights completeness and clarity higher; a stakeholder conflict exercise weights stakeholder consideration higher).

## 9. Feedback Process

Three-stage feedback for every simulation:

**Stage 1: Self-Review** (user-led)
- The user reviews their own deliverable against the scoring rubric
- Guided self-reflection questions help identify gaps
- The user estimates their own score on each dimension

**Stage 2: AI-Generated Feedback** (automated)
- The AI analyzes the deliverable against the model answer
- Specific, line-item feedback on what was done well and what could improve
- Score for each rubric dimension with explanation
- Suggestions for specific improvements

**Stage 3: Model Answer** (reference)
- A complete model deliverable is provided after the user submits
- Not a single "right answer" — shows one valid approach
- Annotated to explain why certain choices were made

## 11. Escalation Events

Mid-simulation events that test the user's ability to handle pressure:

| Event | Trigger | Impact |
|-------|---------|--------|
| **Missing Deadline** | User takes too long on discovery | Manager emails asking for status update; user must reprioritize |
| **Stakeholder Unavailability** | Key stakeholder cancels | User must work with incomplete information and document assumptions |
| **Conflicting Data** | Two sources give contradictory numbers | User must identify discrepancy, investigate, and decide which to trust |
| **Budget Cut** | Mid-project budget reduction announced | User must descope requirements and update the project charter |
| **Resource Conflict** | IT admin says the preferred solution won't work | User must find alternative approach and revalidate with stakeholders |
| **Data Privacy Flag** | Compliance identifies a data handling issue | User must assess impact on requirements and document mitigation |

These events appear randomly or are triggered by specific user actions (or inaction).

## 12. Change-Request Events

Deliberate scope changes that occur after requirements are drafted:

**Scenario A: Regulatory Change**
- A new state regulation requires all caregiver visit records to include a digital signature field
- User must assess which requirements are affected
- Update the RTM, user stories, acceptance criteria, and data dictionary
- Communicate the change to stakeholders

**Scenario B: New Discovery**
- During development, the team discovers the current system has a data export capability no one knew about
- User must reassess integration requirements and potentially simplify the solution

**Scenario C: Priority Shift**
- The agency owner decides caregiver retention is now more important than client acquisition
- User must reprioritize the backlog and explain trade-offs

Each change event produces a required **Change Request** deliverable and an **Impact Analysis**.

## 13. Stakeholder-Conflict Scenarios

Structured scenarios where stakeholders have opposing priorities:

**Conflict 1: Speed vs. Documentation**
- Operations wants the system live in 6 weeks with minimal documentation
- Compliance insists on full documentation, testing, and sign-off before go-live
- The user must facilitate a resolution and document the compromise

**Conflict 2: Features vs. Cost**
- Client services wants maximum functionality for every client type
- Finance wants a minimum viable product to control costs
- The user must lead a MoSCoW prioritization session and produce a phased roadmap

**Conflict 3: Automation vs. Jobs**
- IT wants fully automated scheduling to reduce errors
- The union representing caregivers wants human oversight preserved
- The user must document requirements that balance automation with manual review

**Conflict 4: Data Access vs. Privacy**
- Operations wants full visibility into caregiver performance data
- HR says performance data is confidential and restricted
- The user must design a role-based access model and get sign-off

---

## 14. UAT Scenarios

User Acceptance Testing simulations where a system has been built (simulated data):

**UAT Flow:**
1. User receives a test plan template and the system's documented requirements
2. User designs test scenarios that trace back to specific requirements
3. User executes tests against provided test data (which contains known defects)
4. User identifies defects (incorrect behavior, missing functionality, errors)
5. User writes structured bug reports with severity, steps to reproduce, and evidence
6. User makes a go/no-go recommendation with rationale

**Example Defects Embedded in UAT Scenarios:**
- Scheduling algorithm assigns shifts to unqualified caregivers
- Billing system calculates incorrect overtime rates
- Dashboard KPI shows wrong trend direction (inverted logic)
- Notification system sends alerts to wrong phone numbers
- Export feature omits required fields

## 15. Portfolio-Safe Output Handling

All simulation outputs are clearly identified as practice:

- Every deliverable includes a header: "PRACTICE SIMULATION — Not a real business document"
- No real company, client, patient, or employee data is ever used
- All scenario data is labeled with fictional context
- Users are instructed never to include real data in their practice work
- Output files are stored locally and never shared without user consent
- The lab does not collect or store user deliverables on any server

## 18. Recommended Future Architecture

Two possible implementation paths:

### Option A: Standalone Application
- Separate project from BA Compass (keeps portfolio project clean)
- Frontend: Next.js or React with a scenario state machine
- Storage: LocalStorage for progress, optional cloud sync
- AI: Integrated LLM API (user-provided key) for stakeholder simulation
- No authentication, no backend, no database needed for v1

### Option B: Module Within BA Compass
- A new route within the existing BA Compass Next.js app
- Reuses existing BrightCare Home Services data and stakeholder definitions
- Adds simulation-specific components (timer, chat interface, scoring form)
- Could be gated behind a "Practice Mode" toggle

**Recommended: Option A.** The simulation lab has fundamentally different interaction patterns (conversational, timed, iterative) than BA Compass (documentation, read-only, reference). A separate project avoids architectural compromise and simplifies development iteration.

**Key Technical Considerations:**
- Simulation state must persist across page refreshes
- AI responses should be deterministic enough to give consistent feedback
- Scoring must be fair across different valid approaches
- All data stays client-side for privacy and zero infrastructure cost

## 19. Definition of Done

The Simulation Lab is considered complete when:

1. At least 15 simulations exist across all three difficulty levels
2. Each simulation has a model answer and scoring rubric
3. AI stakeholder simulation produces realistic, scenario-appropriate responses
4. Users can complete a full simulation lifecycle (briefing through reflection)
5. Feedback is specific, actionable, and references the rubric
6. Skills tracker accurately reflects user performance
7. All deliverables are downloadable as Markdown or PDF
8. No user data is transmitted to any server
9. At least 5 users have completed all simulations in beta testing
10. Average user satisfaction rating is 4/5 or higher in beta testing
