# BA Interview Preparation Kit

## 1. The Core Narrative (60-Second Pitch)

> *"Most small businesses spend $1,000–$2,500 per month on software subscriptions that don't talk to each other. I identify these inefficiencies, calculate the exact cost, and build custom solutions that replace 5-8 tools with one unified system — cutting costs by 90% while improving data flow between departments."*

## 2. Common BA Interview Questions

### Q: "Walk me through a project from start to finish."
**The DocFlow Story:**
1. **Discovery** — Mapped document workflow across departments. Found 3 separate subscriptions (Adobe Acrobat, DocuSign, Trello) used for what was essentially one process.
2. **Analysis** — Calculated $46,800/year cost for 50 employees. Interviews revealed 80% of paid features were unused.
3. **Requirements** — Defined core needs: merge, split, compress, sign, track. Nothing else.
4. **Build** — Developed DocFlow as a native Windows app (PySide6). 900 lines of code. Single EXE.
5. **Results** — Saved the company $46,800/year. Break-even in month one. Zero recurring costs.

### Q: "How do you gather requirements?"
- **Stakeholder interviews** — "What frustrates you about the current process?"
- **Process observation** — Watch how the work actually happens, not how people say it happens.
- **Artifact review** — Collect emails, tickets, documents that show the current workflow.
- **Quantitative analysis** — Measure time spent, error rates, costs.
- **The 5 Whys** — Keep asking "why" until you reach the root need.

### Q: "How do you handle scope creep?"
- **Trace everything to requirements** — Every feature must tie back to a documented need.
- **MVP first** — Build the minimum that delivers value. Add features only after validation.
- **Cost visibility** — Show stakeholders the cost of each addition in time/money.
- **Phase 2 bucket** — Nice-to-haves go into a separate list, not the current sprint.

### Q: "Tell me about a time you had to push back on a stakeholder."
- "A stakeholder wanted to add 15 features to DocFlow before launch. I mapped each feature to the original problem statement. Only 4 of the 15 addressed the core issue. The other 11 were nice-to-haves. We launched with the core 4, validated value in week one, and the stakeholder agreed the rest could wait."

### Q: "How do you measure success?"
- **ROI** — Dollars saved vs. cost of building
- **Time saved** — Hours per week before/after
- **Adoption rate** — % of team using the solution
- **Error reduction** — Mistakes before/after
- **Stakeholder satisfaction** — Follow-up interviews

## 3. Business Analysis Framework (Use for Case Studies)

| Step | Question to Answer | Deliverable |
|------|-------------------|-------------|
| **1. Current State** | What's happening now? | Process map, cost data |
| **2. Pain Points** | What's broken? | Pain point matrix |
| **3. Future State** | What should happen? | Target process map |
| **4. Gap Analysis** | What's missing? | Requirements document |
| **5. Solution** | How do we get there? | Build plan, timeline, ROI |
| **6. Validation** | Did it work? | Metrics, stakeholder feedback |

## 4. Key Differentiators (Why YOU)

1. **You can build.** Most BAs hand requirements to developers. You hand requirements AND a working application.
2. **You understand cost.** You quantify problems in dollars, not just pain points.
3. **You know open-source.** You're not tied to vendor ecosystems. You build from scratch.
4. **You think in systems.** Not one-off tools, but integrated suites that solve real business problems.
5. **You deliver production code.** Not prototypes. Compiled EXEs with installers, tested and deployed.
